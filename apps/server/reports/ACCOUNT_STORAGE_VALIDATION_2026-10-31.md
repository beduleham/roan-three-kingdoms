# 로컬 계정 영구 저장 검증 · 2026-10-31

## 변경 파일과 기능

- `apps/server/src/accounts.ts`: SQLite 계정 저장소와 테스트용 메모리 저장소. Google subject 고유 제약, 내부 UUID, 표시 이름·생성 시각·마지막 로그인 시각, 스키마 버전 1과 트랜잭션 초기화.
- `apps/server/src/auth.ts`, `index.ts`: 검증한 Google 신원을 계정 레코드로 연결하고 실제 서버의 기본 저장소를 SQLite로 설정. `ACCOUNT_DB_PATH`, 정상 종료 시 DB 닫기, 저장 실패 시 HTTP 503과 세션 발급 중단.
- `apps/server/test/accounts.test.ts`, `auth.test.ts`: 독립 프로세스 저장/재개, 여러 연결의 동일 계정 ID, SQL 매개변수, DB 손상·미지원 버전·경로 오류·초기화 롤백, 인증과 저장소 경계 검증.
- `package.json`, `package-lock.json`: 내장 SQLite 사용을 위해 최소 Node 22.13 지정. 추가 DB 패키지 없음.
- `.gitignore`: 런타임 계정 DB와 환경 설정 제외.
- `apps/client/vite.config.ts`, `e2e/online.spec.mjs`: 기본 계정 DB와 WAL/SHM 파일의 개발 서버 직접 접근·raw 접근 거부 검사.
- 루트/서버 README, Google 인증 문서, Phase 5 계약, 개발 체크리스트: 저장 경로·지원 범위·제약 갱신.

Node 24.22.1에서 검사했다. 테스트용 별도 Node 프로세스 두 개가 같은 DB를 열어 이름을 갱신해도 기존 내부 ID와 생성 시각이 유지됐다. 인증 서비스를 재생성하면 이전 앱 세션을 거부하고 재로그인 시 같은 계정 ID에 연결했다. 게스트와 잘못된 Google 토큰은 계정 저장을 호출하지 않았다. 저장소 오류 응답에 내부 파일 경로가 포함되지 않고, 실행 중 저장소 오류가 있어도 게스트 방을 만들 수 있음을 확인했다.

기존 로그인 UI 계약·게스트·초대·로비·재접속·타인 명령 거부·시야 검사는 유지됐다. 같은 SQLite 파일을 여는 연결 간 subject 중복 생성을 막고 DB 파일 손상/다른 스키마를 조용히 초기화하지 않음을 검사했다. POSIX에서 새 DB 파일의 권한 0600도 확인했다.

## 구현하지 않은 범위와 다음 조건

실제 Google 웹 클라이언트 ID가 없어 Google 계정 팝업/동의 화면·공개 키 다운로드를 통한 실제 로그인 검증은 여전히 남아 있다. 인증 자동 테스트는 테스트 RSA 인증서로 키 다운로드만 대체하며, 브라우저 Google 로그인 성공 경로는 모의 GIS/인증 HTTP 계약 검사다.

앱 세션·nonce·Room·30초 재접속 예약은 메모리에 남는다. 계정 저장은 경기 진행 상태나 세션을 서버 재시작 뒤 복원하는 기능이 아니다. 성장값·경기 결과·게스트 기록 병합·계정 차단·삭제·다중 서버 공유 세션·백업 자동화는 추가하지 않았다. 전투 규칙과 밸런스는 변경하지 않았다.

영구 볼륨에 같은 DB 경로를 유지해야 한다. 현재 동기 SQLite는 단일 호스트 시연 범위다. Node 22/24 내장 SQLite API의 실험 단계 제약을 인증 문서에 명시했다. 이번 변경에서 900tick 장시간 검사와 Phase 4 로컬 브라우저 전체 검사는 재실행하지 않았다.
